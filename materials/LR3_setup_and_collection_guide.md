# Как запустить сбор данных для ЛР №3

Рабочий адрес для этой версии: https://indolentmenace.github.io/hubspot-lab3/ . Сначала проверить, что сайт открывается без авторизации, затем указывать этот адрес в счётчиках.

1. Google Analytics: войти в свой аккаунт → Администратор → Создать ресурс. Название «HubSpot — ЛР3». Часовой пояс: Москва; валюта: USD. Создать поток данных «Веб», указать адрес сайта. Скопировать Measurement ID вида G-XXXXXXXXXX. Это не числовой Property ID и не секретный API-ключ.

2. Яндекс Метрика: войти в свой аккаунт → добавить счётчик «HubSpot — ЛР3». Указать адрес сайта и часовой пояс Москвы. Для данного проекта Вебвизор не включать. Скопировать числовой номер счётчика.

3. Передать только эти два публичных идентификатора для подключения или вписать их самостоятельно в config.js: window.LAB_CONFIG = { ga4: "G-…", metrica: "12345678" };. Пароли и токены доступа не нужны.

4. Сохранить config.js в репозитории и дождаться обновления GitHub Pages. Проверить, что опубликованный config.js содержит правильные ID. Код счётчиков уже предусмотрен — второй раз через GTM или расширение его не добавлять.

5. В GA4 создать/пометить demo_request как ключевое событие до основного сбора. В настройках потока, если включено автоматическое отслеживание взаимодействий с формами, отключить его для этого опыта или не использовать его события в расчётах: воронка опирается на собственные request_start и demo_request.

6. В Метрике создать цели типа «Целевое событие» с идентификаторами: cta_click, demo_start, demo_step, demo_complete, request_start, demo_request. Использовать точное совпадение имён. Если интерфейс называет тип «JavaScript-событие», ориентироваться на ввод идентификатора и метод reachGoal.

Готовность к исследованию определяется появлением настоящих событий в ваших аккаунтах. Само наличие кода в репозитории этого не подтверждает.



# Проверка до приглашения участников

Открыть техническую ссылку: https://indolentmenace.github.io/hubspot-lab3/?utm_source=qa&utm_medium=test&utm_campaign=lab3_qa&debug=1&_ym_debug=2

Согласиться на аналитику. Нажать Try the interactive demo, пройти три шага и Finish. Выбрать оба значения формы, поставить учебное подтверждение и отправить. Второе нажатие отправки в той же загрузке не должно давать новое событие.

GA4: Администратор → Отображение данных → DebugView (расположение зависит от версии интерфейса). Выбрать своё устройство. Ожидать page_view, demo_start, demo_step, demo_complete, request_start, demo_request. Параметр debug=1 на подготовленном сайте включает debug_mode для Google tag.

В GA4 Realtime проверить поступление текущего визита. Не путать успешную техническую проверку с итоговым исследованием. Обычные участники используют ссылки без debug=1 и без qa.

Метрика: параметр _ym_debug=2 открывает диагностику. Проверить номер счётчика и достижение нужной цели. При необходимости открыть консоль браузера: должен быть вызов Reach goal для demo_request. После обработки проверить целевой визит в отчёте.

Если есть только одна система: проверить соответствующий ID, согласие и загрузку gtag.js или tag.js. В Network браузера искать запросы Google Analytics и mc.yandex.ru. Код ответа запроса — технический признак отправки, а окончательное подтверждение — событие в нужном ресурсе.

Если не работает ни одна: проверить согласие, ошибки JavaScript, опубликованный config.js, доступность сети и блокировщики. Для диагностики владелец может проверить чистый профиль браузера; не обходить отказ участника от аналитики.

Если Realtime работает, а стандартные отчёты пусты: проверить даты, фильтры и ресурс; дать GA4 до 24–48 часов на обработку. Если срок близко, сразу сохранить реальные Realtime/DebugView как техническое подтверждение, но не выдавать их за полноценный ретроспективный отчёт.

Не включать без проверки активный фильтр разработческого/внутреннего трафика: он может исключить нужные события. Технические визиты отделяются UTM и фильтром отчёта. Исправление установки требует повторного реального прохода.



# GA4: как получить нужные метрики

1. Открыть «Исследования» → «Свободная форма». Выбрать календарные даты исследования; в таблице использовать сеансы (Sessions). Период должен полностью охватывать исследование по московскому времени.

2. Добавить измерения Session campaign, Session source/medium, Device category, Event name. Базовое условие: Session campaign = lab3_pilot. Техническая кампания lab3_qa не включается.

3. Создать сегменты сеансов, содержащих событие demo_start, demo_complete, request_start и demo_request. Для каждого сегмента вывести Sessions. Это даст D, C, F, L. При ограничении четырьмя сегментами на одну вкладку использовать две вкладки; общий S взять из таблицы всех сеансов lab3_pilot.

4. Отдельно создать сегменты сеансов Device category = mobile и desktop. Либо вывести Device category строками при общем сегменте lab3_pilot, затем применить сегмент сеансов с demo_request для целевых сеансов устройств.

5. Для групп приглашения вывести Session source/medium и не заменять их First user source/medium: последний относится к первому привлечению пользователя и отвечает на другой вопрос.

6. Если преподаватель требует именно аудитории в интерфейсе GA4, до приглашений дополнительно создать пользовательские аудитории mobile, desktop и demo_request. Их накопление начинается после создания; для анализа уже собранного периода использовать сегменты исследований.

7. Сохранить скриншот условий сегмента и отчёт с видимыми датами. Выгрузить таблицу и перенести Sessions в «Факт» книги XLSX. В числитель CR не ставить Event count: один сеанс может содержать несколько вызовов события.

Если отчёт скрывает строки или выводит предупреждение о качестве данных, сохранить предупреждение вместе с результатом. Не заменять отсутствующую демографию догадками: для этой работы достаточно источника, устройства и действий.



# Метрика: как построить сопоставимые отчёты

1. Выставить тот же период, что в GA4. Проверить часовой пояс счётчика и базовый фильтр UTM Campaign = lab3_pilot.

2. В отчёте по посещаемости получить общее число визитов S. В отчёте по UTM проверить источники classmates и friends. Не считать технический qa исследовательским трафиком.

3. Выбрать условия «Визиты, в которых» → достижение цели demo_start. Получить число визитов D. Повторить для demo_complete (C), request_start (F) и demo_request (L). Альтернатива — метрика целевых визитов выбранной цели.

4. Для мобильного и десктопного сегмента добавить условие устройства. Сохранить каждый сегмент. Если доступны планшеты, не объединять их с телефонами без явного правила; сохранить дополнительной строкой.

5. В отчёте по целям различать достижения и целевые визиты. Повторные события могут увеличивать достижения, не увеличивая число визитов с целью. Для CR используется L/S.

6. Сохранить скриншоты с датами, фильтрами и целями. Внести S, D, C, F, L в строки Метрики листа «Факт». Если L>F или C>D, сначала проверить период, сегменты, смену сеанса и определение метрик.

7. По карте кликов можно уточнить, замечают ли участники CTA. Вебвизор в подготовленном коде выключен, поэтому в отчёте нельзя утверждать, что записи сессий были просмотрены.

Сравнивать системы по одинаковым действиям. Абсолютное равенство чисел не гарантируется, а причина каждого существенного расхождения проверяется отдельно.



# Апробация и завершение отчёта

Пригласить ориентировочно 20–30 добровольцев, распределив ссылки по classmates и friends. Не покупать трафик и не запускать рекламу ради этого этапа. Сохранить отдельный список кодов участников без ФИО и контактов.

Сценарий участников свободный: изучить сайт и самостоятельно решить, открывать ли демо и форму. Обязательный проход всей воронки годится только для qa. Отказ от аналитики разрешён; таких людей не учитывать как зарегистрированные системой визиты.

После первых нескольких посещений проверить обе системы. Если одна не получает данные, остановить приглашения, исправить установку и провести новый согласованный период сбора.

После обработки данных заполнить лист «Факт». Проверить три метрики и таблицу «Сравнение». Выбрать три улучшения, каждому сопоставить конкретное число, сегмент и скриншот. На листе «Прогноз по факту» указать обоснованное сценарное допущение роста.

В Word заменить поля [ ] числами, вставить подлинные скриншоты вместо списка доказательств, записать даты и фактическое число участников. Убрать статус рабочей версии только после этого. Пример с 40 сеансами оставить как отдельный учебный расчёт или заменить реальной базой, явно описав прогноз.

В презентации заменить слайд факта, добавить скриншоты GA4 и Метрики, уточнить выбор основной системы и выводы. Репетировать 6–7 минут; не рассказывать все технические настройки.

Перед сдачей открыть сайт и страницу креативов в браузере без авторизации. Проверить ссылки в PDF. Личные панели аналитики открывать преподавателю только при необходимости и без передачи паролей; для отчёта достаточно скриншотов.
